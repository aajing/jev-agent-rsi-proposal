| Research Question | Scientific question | Can a fixed multimodal JEV improve success on previously unseen visual task instances by using its own execution feedback to revise reusable prompts, with unchanged weights, tools, execution loop and inference budgets? Test interface operation, image/document reasoning, document-driven interface workflows and four games together: Sokoban, a key-and-door maze, no-guess Minesweeper and the fifteen-puzzle. Validation and hidden evaluation contain the same 16 task types, with the same generators, difficulty strata and success rules; only instances differ. One final prompt package serves all types without learning across hidden episodes. |
| Research Question | Why this is scientific research rather than pure engineering optimization | The hypothesis is that transferable instructions about observation, planning, evidence use, error recovery and completion checks improve a frozen model's behavior. Research variables are initial policy text, evolution instructions and reusable textual memory. Compare an unchanged prompt, a fixed self-revision baseline and researcher-designed prompt packages under the same episode protocol; compare evolved candidates with the self-revision baseline under the same Work procedure. Gains must transfer beyond the public development panel. AutoTrust's prior optimization work motivates this experiment but does not establish visual-agent gains or a causal effect of prompt evolution. |

| Evaluation | Fixed evaluation protocol | Implemented 16 task types: four UI, four document, four document-to-interface workflows and four games. Every type has 8 practice, 2 validation and 6 hidden instances: 128 / 32 / 96 total. Validation and hidden evaluation use exactly the same type set, generator support, difficulty strata, action interface and success rules. Within each type, validation has 1 instance in each of two predefined difficulty strata, while hidden evaluation has 3 per stratum; hidden tasks introduce no new type or harder stratum. Instances and seeds differ, with no duplicate full records. One candidate package is evaluated across every type in one complete run. Calibrate the common difficulty rules on public practice data, then freeze all splits and goal validators before scored research. Never select hidden instances according to model outcomes; these are within-type unseen-instance tests, not unseen-family or pretraining-isolation claims.<br>U/D/X/G episodes allow 12/6/20/32 action calls; crop, page change, invalid action, waiting and finish all consume steps. Games advance only after atomic actions, not elapsed real time. Every baseline and candidate uses the same fixed short-plan interface: one to four unconditional direction moves or cell clicks per call, no intermediate observation, branching, loops, held keys, undo, restart, hints or solver access. Observation helpers and finish are single-action calls. Validate the full output before execution; malformed output consumes a decision without executing. Count every attempted atomic action, including illegal ones; stop before exceeding the atomic cap, on an illegal move or on a terminal state, and discard the unattempted suffix. The whole generated output still counts. Return only the final screenshot and execution/budget status. Games have 32 decision calls and additional atomic-operation caps of 128 for Sokoban/maze and 96 for Minesweeper/fifteen-puzzle. Reference play must win within at most 24 total decision calls, including interrupted batches and no-ops. For level certification, reference-controller Minesweeper batches must be selected only from pre-batch visible clues, with every proposed reveal proved safe. The actor need not submit such proofs and is scored by the engine win condition; clicking an already revealed cell is a counted no-op without chording. First-click safety alone is insufficient. Per-episode scratchpad is at most 128 tokens and resets. Three Work rounds plus the initial development evaluation use at most 152 episodes, 2660 action calls and 3 revision calls. Revision outputs are capped at 3072 tokens. Work ceilings: 2 hours, 2700 JEV calls, 16 million input tokens including images and 750,000 generated tokens including reasoning/discards. Failed calls and retries count. Incomplete three-round production is not silently accepted as a shorter run. Full Judge ceiling: 2 hours. Total trajectory: 24 hours by default, separately recorded extension to 48 hours; at most 12 completed Judge calls including controls, without resetting on extension. |

| Evaluation | Reward or score definition | Let A[t] be complete-task success rate for task type t. Score = 100 × sum(A[t] for the 16 types) / 16, with equal weight per type. With six hidden instances per type, this equals 100 × successful_episodes / 96; the complete 32-instance validation set uses the same macro rule. Report all 16 type scores and the four broad-group scores. Preserve unrounded scores. Each episode succeeds only when every required goal is satisfied; partial native reward does not imply success. Games require the engine to verify the full win predicate; losing a game or stopping without a win is failure, and progress is diagnostic only. Document answers use a fixed typed schema and exact canonical values; monetary amounts use integer minor units. Full marks require a compliant candidate, all 96 episodes evaluated and all 96 successful.<br>Malformed output or an illegal action consumes the defined call/attempt budget and ends the current batch; the episode may continue if no terminal state or budget limit has been reached. A wrong submitted final answer, a native losing terminal state, early finish without satisfying the goal, or episode-budget exhaustion yields a completed task failure worth zero. Invalid artifacts, model/runner crashes, infrastructure errors, global timeout or missing episodes yield no valid overall score. The model cannot declare its own reward. |

| Evaluation | Measures preventing reward hacking | Parse only literal bounded text/JSON, validate complete batches before acting, meter all attempts outside prompts and compute rewards from task-owned state. Judge checks exact workload quotas before inference and accepts only canonical B0 or a valid complete Work envelope. Native full-goal predicates, exact document schemas and engine wins replace self-reported success. No hidden per-episode traces or solution-length certificates enter public feedback. The [existing RSI-Harness Judge lifecycle](https://github.com/OpenRSI-Foundation/OpenRSI-Index/blob/57d9ea7127f91bdde94f89ae47d95cf1ad374836/RSI-Harness/src/rsi_harness/runtime/judge.py#L528) pauses Work, snapshots it, injects operator-owned tests into Judge-only /tests and invokes /tests/test.sh. The Judge-only tests check model/runtime/input manifests, snapshot the candidate JSON and import a tests-injected source copy using Python isolated mode. Judge generates the episodes itself and computes rewards from the task engines; candidate-written predictions or reward files are not scoring inputs. Judge still runs on the inherited Work snapshot, and /tests is a fresh tmpfs injection rather than a read-only or root-proof mount. These controls detect ordinary artifact and dependency changes but do not establish protection against an unrestricted shared-root adversary or cryptographic authenticity of Work history. No separate host controller, signed-receipt service or independent clean-Base verifier is assumed by this proposal. Official Harness/GPU integration remains subsequent task-construction validation. |
